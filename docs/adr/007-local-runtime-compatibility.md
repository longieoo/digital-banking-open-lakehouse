# Local runtime compatibility and service initialization

## Context

The first Docker execution exposed issues that configuration parsing and local SQL
substitutes could not detect: the REST catalog UID could not write its fresh named
volume, Spark's Ivy cache pointed outside the writable mounted directory, Python
3.8 in the pinned Spark image evaluated newer shared type annotations, and Airflow's
preinstalled Python packages conflicted with the dbt/AWS clients.

## Decision

- Initialize only the catalog volume root as UID/GID 1000 before starting REST.
  Keep the REST service itself unprivileged and preserve existing catalog data.
- Limit the SQLite-backed REST fixture to one JDBC client. The default two-client
  pool produced SQLITE_BUSY errors during Gold writes after catalog restart,
  although reads and health checks passed. The acceptance gate now also rebuilds
  Gold after restart. The `clients` setting is defined in the pinned
  [Iceberg CatalogProperties](https://github.com/apache/iceberg/blob/apache-iceberg-1.9.1/core/src/main/java/org/apache/iceberg/CatalogProperties.java).
- Set Spark's Ivy directory explicitly to the existing persistent writable mount.
- Defer annotation evaluation in the shared ingestion module. The application and
  local test environment still require Python 3.11+; the Spark image can import the
  shared standard-library helpers without installing the application package.
- Install dbt in its own virtual environment inside the Airflow image and invoke
  its executable explicitly from the Gold DAG. Keep Airflow's interpreter and
  scheduler dependencies separate. Pin aiobotocore 2.23.1 to match boto3 1.38.46,
  and require pip check during the image build.
- Wait for service health before seeding in the real-stack acceptance script.

## Consequences

These changes preserve the source/raw/Bronze/Silver/Gold design and dependency
versions of the standalone dbt image. They do not replace real service tests with
local substitutes. The integration Spark test also executes all three risk rules
and checks the amount threshold boundary on Spark itself. Linux provider checksums
generated by Terraform initialization are retained alongside the existing hashes.

The local environment remains a single-host educational demo. Azure deployment,
identity enforcement and a Power BI Desktop artifact are separate acceptance gates.
